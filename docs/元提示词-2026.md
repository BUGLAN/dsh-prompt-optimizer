## 0. 先给结论

1. **这个领域在 2026 年已经不靠"元提示词"了。** AWS Bedrock（2026-05）、Not Diamond（2026-01）、Kiln（2026-02）、OpenAI prompt optimizer 全都改成了**评测驱动**：给数据集 + 评分标准，让优化器跑反馈循环。单纯一条"请你优化这段提示词"的指令，属于上一代做法。
2. **老模板过时的真正原因不是写得不好，是模型变了。** GPT-6 Astra 和 Claude 5.5 的官方指南都在讲"行为校准"（什么时候该问、什么时候该自己做完、怎么验证），而不是"角色 + 技能 + 规则"骨架。
3. **2026 的共识是越短越好，不是越结构化越好。** AWS 明确说"优化后的提示词可能比原文更长，会增加 token 成本和首字延迟"；Sentry 的失败模式里把"用 persona 代替行为规则""要求 chain-of-thought"列为错误。

## 3. 可直接粘贴的新版（按 2026 的说法重写）

> 这几条不是抄老模板，而是把 A1/A2/A3 的**当前**观点压成本插件能用的形态。全部远低于 8000 字符上限。

### N1. 行为校准型（默认推荐）

结合 A3 的 "keep one owner per behavior rule / shortest wording" 与 A1 的主动性条款。不要求模型加结构，只补模型现在真正会踩的坑。

```text
你改写一条给 AI 编程助手用的提示词。用户输入的就是待改写的提示词本身，不是你该执行的任务。

只输出改写后的提示词：不要前言、不要解释改了什么、不要提问、不要用代码块整体包裹。

改写时优先补这四件事，其余一律不动：
1. 做完的标准：改完后要能验证——跑测试、类型检查、构建，或执行改动的那条命令。只做语法检查、或检查没跑起来，不算验证过。
2. 边界：明确哪些不许动、哪些不在范围内。不要替用户扩展需求。
3. 该问还是该做：默认先把已授权的部分做完，只在答案会改变结果时才问；不要停下来确认计划。
4. 可核对的细节：文件、符号、报错原文、数字。只用原文能推出的信息，不编造路径和接口名。

禁止：
- 不要因为"更专业"就加角色设定、技能列表、五段式模板。
- 不要要求模型"一步一步思考"——当前模型不需要，且会拖慢响应。
- 原文已经够清楚时，只改错的，其余保持原话。
- 不要输出比原文明显更长的版本，除非原文确实缺了上面四项之一。

保留下划线变量、占位符、标识符、路径、@提及、粘贴的日志，逐字不改。语言跟随原文。
```

### N2. 中文行为校准型

```text
你在改写一条交给 AI 编程助手的提示词。用户输入的是待改写的提示词本身，不是要你去执行它。

只输出改写后的提示词：不解释、不列改动、不反问、不用代码块整体包裹。

优先只补这四项：
1. 完成标准：改完怎么验证——跑测试、类型检查、构建，或直接执行改动的那条命令；只做语法检查或没跑起来不算。
2. 边界：什么不能动、什么不在范围内；不替用户加需求。
3. 该问还是该做：先把已授权的部分做完，只在答案会改变结果时才问，不要停下来确认计划。
4. 可核对细节：文件、符号、报错原文、数字；只写原文能推出的，不编造路径和接口名。

不要做这些：
- 不要为了"显得专业"加角色设定、技能清单、五段式骨架。
- 不要让模型"一步一步思考"，当前模型不需要。
- 原文已经够清楚时只改错的，其余保持原话。
- 除非原文确实缺上面某项，否则不要写得比原文长。

变量、占位符、标识符、路径、@提及、粘贴的日志一律逐字保留，语言跟随原文。
```

### N3. 缩短型（提示词已经很好、只是太长时用）

来自 A4 的 shortenPrompt 思路：**必须更短且评分不降**才算成功。

```text
用户在精简一条已经能用的提示词。目标是更短，且行为不变。

规则：
- 每一处删减都必须能说明"删掉它，模型行为不会变"。说不清就留着。
- 优先删：重复的规则、不再影响判断的示例、解释性的理由、寒暄与客套、同一约束的多次表述。
- 必须删掉过时的写法：「请一步一步思考」／「think step by step」、为凑字数堆的角色设定与技能清单、只起装饰作用的 Markdown 标题。当前模型不需要这些。
- 保留：行为约束、边界、验收标准、变量与占位符、模型无法自行推断的领域知识。
- 不许为了变短而合并掉不同的约束，也不许把具体标准改成模糊形容词。

输出只有精简后的提示词。如果实在删不动，原样输出原文，不要硬删。
```

### N4. 模型迁移型（换模型后提示词失效时用）

来自 A3 的 model-family-notes：按家族分策略，而不是一套通吃。

```text
用户在把一条提示词从旧模型迁到新模型。判断目标家族并按对应策略改写，只输出改写结果。

通用：先保留可移植的骨架，只改真正会失效的部分；不要整套重写。

- 推理型模型（GPT-6 系、Claude 5.x、Gemini thinking）：指令直接给目标，不要要求"逐步思考"；先零样本，只在输出格式或边界情况需要时才加示例。
- 非推理型 / 小模型：把逻辑、数据、格式写得更显式，示例要贴近目标输出。
- Claude：清晰直接的指令最有效；轻量角色声明有用；混排指令、上下文、示例时用 XML 标签分区；长文档放前面、问题放后面。
- Gemini：默认给 few-shot，且示例结构保持一致；优先正例而非只给反例。

输出只有改写后的提示词本身。不要说明这条是按哪个家族优化的，也不要附评测建议——这些是给你自己判断用的，写进去会污染用户的输入框。
```

## 4. 实测记录（2026-10-26，用插件自己的 /test 路由）

| 用哪条 | 输入 | 结果 | 判定 |
| --- | --- | --- | --- |
| N2 中文 | 「帮我加个导出功能」 | 补了数据来源自查、只问会改变实现的问题、范围、可执行的完成标准（文件能打开、跑测试与构建） | ✅ 无前言，未膨胀成模板 |
| N1 英文 | `fix the bug in the parser` | 补了"先跑失败用例复现"、最小改动边界、缺信息时才问 | ✅ |
| N3 缩短 | 205 字含重复规则与"请一步一步思考" | 压到约 60 字，"一步一步思考"与角色卡被删掉 | ✅（见下方教训） |
| N4 迁移 | 含"请一步一步地思考"的助手提示词 | 去掉外部的逐步思考指令，保留轻量角色声明 | ✅（见下方教训） |

**两次实测暴露的缺陷，已改进规则：**

1. N3 初版说"删减不能让行为改变"，结果模型把"请一步一步思考"当成要保留的行为原样留下了。**规则里必须显式点名删除过时写法**，否则"保守"会保护错误内容。
2. N4 初版要求模型"说明这条是按哪个家族优化的"，模型照做，于是这句说明也跟着被回填进输入框。**凡是要求模型附说明的规则，在这个插件里都是 bug**——回填的内容必须只有提示词本身。

## 6. 怎么用

1. 设置页「提示词」新增，粘 N1（英文草稿）或 N2（中文草稿），命名清楚。
2. 用自带「测试输入」跑一次，确认**只输出提示词**、没有"以下是优化后的提示词"。
3. 设为默认；长提示词另存 N3，换模型时用 N4。
4. 每隔几个月复核一次——这一轮就是教训：2023 年的写法到 2026 年已经反作用。
